1 Introduction

Single-cell RNA sequencing (scRNA-seq) measures gene expression in individual cells rather than averaging expression across a bulk tissue sample. Where bulk RNA-seq returns one expression profile per sample, scRNA-seq returns one profile per cell, typically for thousands to tens of thousands of cells in a single experiment. This resolution makes it possible to identify cell types and states that would be invisible in bulk data, characterize rare populations, trace differentiation trajectories, and study cell-to-cell heterogeneity within an otherwise “homogeneous” tissue.

That resolution comes at a cost. Each cell contributes only a small amount of RNA, so the resulting count data are noisy, sparse, and subject to technical artifacts that bulk RNA-seq does not have to contend with in the same way (dropout, variable capture efficiency, ambient RNA contamination, doublets). A large fraction of the analytical effort in any scRNA-seq workflow — arguably the most consequential fraction, since errors here propagate into every downstream result — goes into preprocessing and quality control: deciding which barcodes represent real cells, which genes are usably detected, and how to normalize the resulting count matrix so that expression values are comparable across cells.

This document walks through that preprocessing stage end to end, using the canonical PBMC 3k dataset from 10x Genomics as a worked example. Each section pairs a short conceptual explanation of why a step is done with the runnable R code that does it, so the document can be read either as a tutorial on the concepts or as an executable pipeline (or both, which is the intent of R Markdown).

1.2 About the dataset

PBMC 3k is a peripheral blood mononuclear cell (PBMC) dataset released by 10x Genomics as a public demonstration dataset for their Chromium single-cell 3’ gene expression assay. It contains gene expression measurements for approximately 2,700 single cells, sequenced on an Illumina platform.

Because PBMCs are a mixture of well-characterized immune cell types (T cells, B cells, NK cells, monocytes, dendritic cells) with known marker genes, and because the dataset is small enough to process on a laptop, it has become the de facto “hello world” dataset for benchmarking and teaching single-cell workflows — most single-cell tutorials (including Seurat’s own) use it for exactly this reason.

1.3 The 10x Genomics output format

A 10x Chromium run produces, after alignment and cell calling with cellranger, a sparse count matrix distributed as three files:

  • matrix.mtx — the count matrix itself, stored in MatrixMarket sparse format (only nonzero entries are written to disk, since the vast majority of gene × cell entries are zero)
  • barcodes.tsv — the cell barcode corresponding to each column of the matrix (one barcode = one droplet =, ideally, one cell)
  • genes.tsv / features.tsv — the gene identifiers corresponding to each row of the matrix

Storing the matrix in sparse form is not a minor implementation detail — it is what makes single-cell data tractable at all. A dense matrix for 2,700 cells × ~32,000 genes would need to hold ~86 million entries; the sparse representation only needs to store the nonzero ones, which, as we’ll see below, is a small fraction of that.

3.3 Why sparsity matters

In a typical droplet-based scRNA-seq experiment, the majority of gene × cell entries in the count matrix are zero. This is partly biological (most genes are not expressed in most cell types at any given time) and partly technical — a phenomenon usually called dropout: a transcript that is genuinely present in the cell but is not captured, reverse-transcribed, or sequenced deeply enough to be detected. Distinguishing “true zero” from “dropout zero” is impossible at the level of a single entry, and this ambiguity is one of the central statistical challenges in scRNA-seq analysis (it motivates, among other things, the imputation and modeling choices in methods like SCTransform, discussed later).

4 Creating the Seurat Object

A Seurat object is the central data structure used throughout the workflow. It bundles together the raw count matrix, per-cell metadata (library size, number of genes detected, and anything else computed later such as QC metrics or cluster assignments), and, as the analysis proceeds, normalized data, scaled data, dimensionality-reduction embeddings, and nearest-neighbor graphs — all addressable through one object rather than as separate, easily-desynchronized variables.

At creation time, two basic filters are already applied:

  • min.cells = 3: a gene is kept only if it is detected (count > 0) in at least 3 cells. Genes detected in fewer cells than this are almost always uninformative noise and needlessly inflate the feature space.
  • min.features = 200: a cell (barcode) is kept only if at least 200 genes are detected in it. Barcodes with very few detected genes are usually empty droplets or fragments of lysed cells rather than intact single cells.

These are coarse, standard defaults intended to remove obviously unusable barcodes/genes before any more principled QC is applied — they are not a substitute for the QC step in the next section.

pbmc <- CreateSeuratObject(

4.1 Automatically computed metadata

On creation, Seurat automatically computes two metrics for every cell:

  • nCount_RNA — total UMI (Unique Molecular Identifier) count for the cell, i.e. total library size. UMIs are short random sequences attached to each transcript molecule before amplification, which let Seurat distinguish independent transcript molecules from PCR duplicates of the same molecule — this is why scRNA-seq counts are described as UMI counts rather than raw reads.
  • nFeature_RNA — number of distinct genes detected (count > 0) in the cell.

5 Exploring Single-Cell Data Characteristics

Before doing any filtering or normalization, it is worth building intuition for what makes single-cell count data different from bulk RNA-seq data, since every preprocessing decision downstream is a response to one of these properties.

Single-cell count data are characterized by:

  1. Sparsity — most gene/cell entries are zero (shown above)
  2. High cell-to-cell variability — even cells of the same type differ in library size and detected gene count, partly biology, partly technical variation in capture efficiency
  3. Technical noise — amplification bias, batch effects, and sequencing depth all affect the observed counts independently of true expression
  4. Dropout — false zeros, as discussed above

6 Quality Control and Preprocessing

With the raw object built and its general character understood, we now compute the metrics used to decide which cells (and, later, which genes) should be retained for downstream analysis.

6.1 Why mitochondrial content matters

Cells that are dying, ruptured, or otherwise stressed tend to lose cytoplasmic mRNA through membrane damage while retaining mitochondrial mRNA somewhat longer, because mitochondria are membrane-bound organelles. The practical consequence is that a high proportion of a cell’s transcripts mapping to mitochondrial genes is a strong signal of a low-quality or dying cell rather than a genuine biological state (with a few tissue-specific exceptions, e.g. cardiomyocytes, which are not relevant to PBMCs). Human mitochondrial genes are conventionally identified by the MT- gene symbol prefix.

Ribosomal gene content (RPS/RPL prefixes) is tracked as a secondary, optional QC signal — it is more informative as a marker of cell-type-specific translational activity than of cell viability, but unusually low or unusually high values can still flag technical issues.

6.3 Setting filtering thresholds

There are two broad philosophies for choosing QC thresholds, and the code below demonstrates both so they can be compared.

1. Statistical / data-driven thresholding. Compute a robust measure of central tendency and spread for each metric — the median and the median absolute deviation (MAD) rather than the mean and standard deviation, because MAD is far less sensitive to the extreme outliers that scRNA-seq QC metrics routinely contain — and flag cells beyond some multiple of MAD from the median (3 MAD is a common convention, roughly analogous to a z-score cutoff but robust to outliers).

2. Literature-based / conventional thresholding. Use fixed, commonly cited cutoffs from the literature and from widely used tutorials (e.g. the original Seurat PBMC3k vignette): nFeature_RNA between 200 and 2500, and percent.mt below 20%. These are less tailored to the specific dataset but are simple, well-precedented, and easy to communicate.

Neither approach is objectively “correct” — the data-driven approach adapts to the specific sample but can be thrown off by a dataset that genuinely contains many low-quality cells (inflating the MAD and loosening the threshold accordingly); the literature-based approach is stable but was calibrated on other datasets and assays. In practice, both are computed and compared, and the final choice is a judgment call cross-checked against the QC plots above.

7 Normalization

7.1 Why normalize at all

Raw UMI counts are not directly comparable between cells, because two cells expressing a gene at the same true level can produce very different raw counts simply due to differences in sequencing depth (total UMIs captured per cell). Normalization aims to remove this technical, depth-driven variation so that differences in expression values between cells reflect biology rather than how deeply each cell happened to be sequenced.

Two conceptually different normalization strategies are demonstrated here.

7.1.1 Method 1 — Log-normalization

The traditional approach: scale each cell’s counts by its total UMI count, multiply by a constant scale factor (10,000 by convention, chosen simply to bring values into a convenient range), and log-transform (log1p, i.e. log(1 + x), to handle zeros):

\[ x_{ij}^{\text{norm}} = \log\left(1 + \frac{x_{ij}}{\sum_j x_{ij}} \times 10{,}000\right) \]

where (x_{ij}) is the raw count of gene (i) in cell (j). This is fast, simple, and the historical default, but it treats every cell’s total count as an equally reliable estimate of sequencing depth and does not explicitly model the count distribution’s variance structure.

Code 
pbmc_log <- pbmc_filtered
pbmc_log <- NormalizeData(pbmc_log, normalization.method = "LogNormalize",
                          scale.factor = 10000)
cat("Log-normalization completed.\n")
Log-normalization completed.

7.1.2 Method 2 — SCTransform

SCTransform takes a model-based approach: it fits a regularized negative binomial regression of each gene’s counts against sequencing depth across all cells, pooling information across genes to regularize the per-gene model parameters (since fitting each gene’s model independently would be noisy for lowly-expressed genes). The Pearson residuals from this model — the deviation of each observed count from what the depth-based model predicts — are used as the normalized expression values.

This has two practical advantages over log-normalization: it does not require a separate downstream step to identify highly variable genes (the model naturally highlights genes whose variance exceeds what sequencing depth alone would predict), and it tends to better stabilize variance across the full range of expression levels, including for lowly-expressed genes where log-normalization is known to under- or over-correct. The tradeoff is computational cost and, for some users, reduced interpretability of the resulting values relative to a straightforward log ratio.

  • pbmc_filtered.rds — QC-filtered, not yet normalized (raw counts only)
  • pbmc_log_normalized.rds — log-normalized (RNA assay, data layer)
  • pbmc_sct_normalized.rds — SCTransform-normalized (SCT assay)

Either normalized object is a valid starting point for the next stage of a standard scRNA-seq workflow, which is not covered in this document:

  1. Feature selection — identifying highly variable genes to focus downstream steps on the genes carrying the most biological signal
  2. Dimensionality reduction — PCA (and, for visualization, UMAP/t-SNE) to compress the noisy, high-dimensional expression matrix into a tractable number of components
  3. Clustering — grouping cells into putative cell populations based on similarity in the reduced-dimensional space (typically graph-based clustering, e.g. Louvain/Leiden on a shared-nearest-neighbor graph)
  4. Cell type annotation — assigning biological identity to each cluster using canonical marker genes or reference-based label transfer
  5. Differential expression — comparing expression between clusters or conditions to identify marker genes or condition-specific responses

Each of these steps depends critically on the QC and normalization decisions made above — an under-filtered or poorly normalized input propagates errors into every subsequent step — which is why this stage, despite producing no biological “results” of its own, is treated as foundational rather than a formality.

# Introduction

Single-cell RNA sequencing (scRNA-seq) measures gene expression in individual
cells rather than averaging expression across a bulk tissue sample. Where
bulk RNA-seq returns one expression profile per sample, scRNA-seq returns one
profile *per cell*, typically for thousands to tens of thousands of cells in
a single experiment. This resolution makes it possible to identify cell
types and states that would be invisible in bulk data, characterize rare
populations, trace differentiation trajectories, and study cell-to-cell
heterogeneity within an otherwise "homogeneous" tissue.

That resolution comes at a cost. Each cell contributes only a small amount of
RNA, so the resulting count data are noisy, sparse, and subject to technical
artifacts that bulk RNA-seq does not have to contend with in the same way
(dropout, variable capture efficiency, ambient RNA contamination, doublets).
A large fraction of the analytical effort in any scRNA-seq workflow —
arguably the most consequential fraction, since errors here propagate into
every downstream result — goes into **preprocessing and quality control**:
deciding which barcodes represent real cells, which genes are usably
detected, and how to normalize the resulting count matrix so that
expression values are comparable across cells.

This document walks through that preprocessing stage end to end, using the
canonical **PBMC 3k** dataset from 10x Genomics as a worked example. Each
section pairs a short conceptual explanation of *why* a step is done with
the runnable R code that does it, so the document can be read either as a
tutorial on the concepts or as an executable pipeline (or both, which is the
intent of R Markdown).

1. The structure of 10x Genomics data and how it is loaded into R
2. Construction and anatomy of a `Seurat` object
3. Data exploration: sparsity, distributions of library size and gene detection
4. Quality-control metrics, in particular mitochondrial and ribosomal content
5. Statistical vs. literature-based thresholding strategies for filtering
6. Cell- and gene-level filtering

## About the dataset

**PBMC 3k** is a peripheral blood mononuclear cell (PBMC) dataset released
by 10x Genomics as a public demonstration dataset for their Chromium
single-cell 3' gene expression assay. It contains gene expression
measurements for approximately 2,700 single cells, sequenced on an Illumina
platform.

Because PBMCs are a mixture of well-characterized immune cell types (T
cells, B cells, NK cells, monocytes, dendritic cells) with known marker
genes, and because the dataset is small enough to process on a laptop, it
has become the de facto "hello world" dataset for benchmarking and teaching
single-cell workflows — most single-cell tutorials (including Seurat's own)
use it for exactly this reason.

## The 10x Genomics output format

A 10x Chromium run produces, after alignment and cell calling with
`cellranger`, a sparse count matrix distributed as three files:

- **`matrix.mtx`** — the count matrix itself, stored in MatrixMarket sparse
  format (only nonzero entries are written to disk, since the vast majority
  of gene × cell entries are zero)
- **`barcodes.tsv`** — the cell barcode corresponding to each column of the
  matrix (one barcode = one droplet =, ideally, one cell)
- **`genes.tsv` / `features.tsv`** — the gene identifiers corresponding to
  each row of the matrix

Storing the matrix in sparse form is not a minor implementation detail — it
is what makes single-cell data tractable at all. A dense matrix for 2,700
cells × ~32,000 genes would need to hold ~86 million entries; the sparse
representation only needs to store the nonzero ones, which, as we'll see
below, is a small fraction of that.

## Why sparsity matters

In a typical droplet-based scRNA-seq experiment, the majority of gene ×
cell entries in the count matrix are zero. This is partly biological (most
genes are not expressed in most cell types at any given time) and partly
technical — a phenomenon usually called **dropout**: a transcript that is
genuinely present in the cell but is not captured, reverse-transcribed, or
sequenced deeply enough to be detected. Distinguishing "true zero" from
"dropout zero" is impossible at the level of a single entry, and this
ambiguity is one of the central statistical challenges in scRNA-seq analysis
(it motivates, among other things, the imputation and modeling choices in
methods like `SCTransform`, discussed later).

```{r sparsity_check}
non_zero_pct <- round(100 * sum(pbmc.data > 0) / (nrow(pbmc.data) * ncol(pbmc.data)), 2)
cat("Percentage of non-zero entries in the raw matrix:", non_zero_pct, "%\n")
```

Storing this matrix in sparse format (rather than as a dense matrix) is what
keeps memory usage manageable — the object only stores the coordinates and
values of nonzero entries.

# Creating the Seurat Object

A `Seurat` object is the central data structure used throughout the
workflow. It bundles together the raw count matrix, per-cell metadata
(library size, number of genes detected, and anything else computed later
such as QC metrics or cluster assignments), and, as the analysis proceeds,
normalized data, scaled data, dimensionality-reduction embeddings, and
nearest-neighbor graphs — all addressable through one object rather than as
separate, easily-desynchronized variables.

At creation time, two basic filters are already applied:

- **`min.cells = 3`**: a gene is kept only if it is detected (count > 0) in
  at least 3 cells. Genes detected in fewer cells than this are almost
  always uninformative noise and needlessly inflate the feature space.
- **`min.features = 200`**: a cell (barcode) is kept only if at least 200
  genes are detected in it. Barcodes with very few detected genes are
  usually empty droplets or fragments of lysed cells rather than intact
  single cells.

These are coarse, standard defaults intended to remove obviously unusable
barcodes/genes before any more principled QC is applied — they are not a
substitute for the QC step in the next section.

## Automatically computed metadata

On creation, Seurat automatically computes two metrics for every cell:

- **`nCount_RNA`** — total UMI (Unique Molecular Identifier) count for the

  distinguish independent transcript molecules from PCR duplicates of the
  same molecule — this is why scRNA-seq counts are described as UMI counts
  rather than raw reads.
- **`nFeature_RNA`** — number of distinct genes detected (count > 0) in the

# Exploring Single-Cell Data Characteristics

Before doing any filtering or normalization, it is worth building intuition
for what makes single-cell count data different from bulk RNA-seq data,
since every preprocessing decision downstream is a response to one of these
properties.

Single-cell count data are characterized by:

1. **Sparsity** — most gene/cell entries are zero (shown above)
2. **High cell-to-cell variability** — even cells of the same type differ in
   library size and detected gene count, partly biology, partly technical
   variation in capture efficiency
3. **Technical noise** — amplification bias, batch effects, and
   sequencing depth all affect the observed counts independently of true
   expression
4. **Dropout** — false zeros, as discussed above

# Quality Control and Preprocessing

With the raw object built and its general character understood, we now
compute the metrics used to decide which cells (and, later, which genes)
should be retained for downstream analysis.

## Why mitochondrial content matters

Cells that are dying, ruptured, or otherwise stressed tend to lose
cytoplasmic mRNA through membrane damage while retaining mitochondrial mRNA
somewhat longer, because mitochondria are membrane-bound organelles. The
practical consequence is that a **high proportion of a cell's transcripts
mapping to mitochondrial genes** is a strong signal of a low-quality or
dying cell rather than a genuine biological state (with a few
tissue-specific exceptions, e.g. cardiomyocytes, which are not relevant to
PBMCs). Human mitochondrial genes are conventionally identified by the
`MT-` gene symbol prefix.

## Setting filtering thresholds

There are two broad philosophies for choosing QC thresholds, and the code
below demonstrates both so they can be compared.

**1. Statistical / data-driven thresholding.** Compute a robust measure of
central tendency and spread for each metric — the median and the **median
absolute deviation (MAD)** rather than the mean and standard deviation,
because MAD is far less sensitive to the extreme outliers that scRNA-seq QC
metrics routinely contain — and flag cells beyond some multiple of MAD from
the median (3 MAD is a common convention, roughly analogous to a
z-score cutoff but robust to outliers).

**2. Literature-based / conventional thresholding.** Use fixed, commonly
cited cutoffs from the literature and from widely used tutorials (e.g. the
original Seurat PBMC3k vignette): `nFeature_RNA` between 200 and 2500, and
`percent.mt` below 20%. These are less tailored to the specific dataset but
are simple, well-precedented, and easy to communicate.

Neither approach is objectively "correct" — the data-driven approach adapts
to the specific sample but can be thrown off by a dataset that genuinely
contains many low-quality cells (inflating the MAD and loosening the
threshold accordingly); the literature-based approach is stable but was
calibrated on other datasets and assays. In practice, both are computed and
compared, and the final choice is a judgment call cross-checked against the
QC plots above.

# Normalization

## Why normalize at all

Raw UMI counts are not directly comparable between cells, because two cells
expressing a gene at the same *true* level can produce very different raw
counts simply due to differences in sequencing depth (total UMIs captured
per cell). Normalization aims to remove this technical, depth-driven
variation so that differences in expression values between cells reflect
biology rather than how deeply each cell happened to be sequenced.

Two conceptually different normalization strategies are demonstrated here.

### Method 1 — Log-normalization

The traditional approach: scale each cell's counts by its total UMI count,
multiply by a constant scale factor (10,000 by convention, chosen simply to
bring values into a convenient range), and log-transform (`log1p`, i.e.
`log(1 + x)`, to handle zeros):

$$
x_{ij}^{\text{norm}} = \log\left(1 + \frac{x_{ij}}{\sum_j x_{ij}} \times 10{,}000\right)
$$

where \(x_{ij}\) is the raw count of gene \(i\) in cell \(j\). This is fast,
simple, and the historical default, but it treats every cell's total count
as an equally reliable estimate of sequencing depth and does not explicitly
model the count distribution's variance structure.

```{r log_normalize}
pbmc_log <- pbmc_filtered
pbmc_log <- NormalizeData(pbmc_log, normalization.method = "LogNormalize",
                          scale.factor = 10000)
cat("Log-normalization completed.\n")
```

### Method 2 — SCTransform

`SCTransform` takes a model-based approach: it fits a **regularized
negative binomial regression** of each gene's counts against sequencing
depth across all cells, pooling information across genes to regularize the
per-gene model parameters (since fitting each gene's model independently
would be noisy for lowly-expressed genes). The Pearson residuals from this
model — the deviation of each observed count from what the depth-based
model predicts — are used as the normalized expression values.

This has two practical advantages over log-normalization: it does not
require a separate downstream step to identify highly variable genes (the
model naturally highlights genes whose variance exceeds what sequencing
depth alone would predict), and it tends to better stabilize variance across
the full range of expression levels, including for lowly-expressed genes
where log-normalization is known to under- or over-correct. The tradeoff is
computational cost and, for some users, reduced interpretability of the
resulting values relative to a straightforward log ratio.

```{r sctransform}
pbmc_sct <- pbmc_filtered
pbmc_sct <- SCTransform(pbmc_sct, verbose = FALSE)
cat("SCTransform normalization completed.\n")
```

## Comparing the two methods

As a concrete illustration, we compare raw, log-normalized, and
SCTransform-normalized values for **CD3D**, a canonical marker of T cells
and one of the more variably expressed genes in a PBMC population — a good
stress test for how each method handles a gene with real biological
heterogeneity across cell types.

```{r compare_normalization}
if ("CD3D" %in% rownames(pbmc_filtered[["RNA"]])) {

  raw_counts <- GetAssayData(pbmc_filtered, assay = "RNA", layer = "counts")["CD3D", ]
  log_norm   <- GetAssayData(pbmc_log, assay = "RNA", layer = "data")["CD3D", ]
  sct_norm   <- pbmc_sct@assays$SCT@data["CD3D", ]

  norm_comparison <- data.frame(
    Raw         = as.numeric(raw_counts),
    LogNorm     = as.numeric(log_norm),
    SCTransform = as.numeric(sct_norm)
  )

  # Drop cells where the gene is undetected under every method
  norm_comparison <- norm_comparison[rowSums(norm_comparison) > 0, ]

  norm_long <- melt(norm_comparison)

  p_norm_comparison <- ggplot(norm_long, aes(x = variable, y = value, fill = variable)) +
    geom_boxplot() +
    labs(title = "CD3D Expression: Normalization Method Comparison",
         x = "Normalization Method", y = "Expression Value") +
    theme_minimal() +
    theme(legend.position = "none")

  p_norm_comparison

  ggsave(file.path(base_dir, "plots", "normalization_comparison.png"),
         p_norm_comparison, width = 8, height = 6)
}
```

Raw counts and the two normalized versions live on different scales by
construction, so the comparison above is about *shape* (spread, skew,
separation between expressing and non-expressing cells) rather than absolute
magnitude — a well-behaved normalization should compress the extreme
right-skew of the raw counts while still preserving the separation between
CD3D-high (T cell) and CD3D-low/absent (everything else) cells.

# Summary and Next Steps

At this point the pipeline has produced three saved `Seurat` objects, all
built on the same QC-filtered set of cells and genes but carrying different
normalizations:

- `pbmc_filtered.rds` — QC-filtered, **not yet normalized** (raw counts only)
- `pbmc_log_normalized.rds` — log-normalized (`RNA` assay, `data` layer)
- `pbmc_sct_normalized.rds` — SCTransform-normalized (`SCT` assay)

Either normalized object is a valid starting point for the next stage of a
standard scRNA-seq workflow, which is not covered in this document:

1. **Feature selection** — identifying highly variable genes to focus
   downstream steps on the genes carrying the most biological signal
2. **Dimensionality reduction** — PCA (and, for visualization, UMAP/t-SNE)
   to compress the noisy, high-dimensional expression matrix into a
   tractable number of components
3. **Clustering** — grouping cells into putative cell populations based on
   similarity in the reduced-dimensional space (typically graph-based
   clustering, e.g. Louvain/Leiden on a shared-nearest-neighbor graph)
4. **Cell type annotation** — assigning biological identity to each cluster
   using canonical marker genes or reference-based label transfer
5. **Differential expression** — comparing expression between clusters or
   conditions to identify marker genes or condition-specific responses

Each of these steps depends critically on the QC and normalization
decisions made above — an under-filtered or poorly normalized input
propagates errors into every subsequent step — which is why this stage,
despite producing no biological "results" of its own, is treated as
foundational rather than a formality.
